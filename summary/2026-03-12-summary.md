### 二、核心概念纠正

#### 1. BFC vs 层叠上下文（重要！）

| 概念 | 作用 | 触发条件 |
|------|------|----------|
| BFC | 解决布局问题（浮动、margin 重叠） | overflow:hidden, float, display:flex, position:absolute/fixed |
| 层叠上下文 | 控制 z 轴层级 | position+z-index, transform, opacity, will-change |

**用户混淆点：** `transform` 创建的是层叠上下文，不是 BFC！

#### 2. position 触发条件

```css
/* 会触发 BFC */
position: absolute;  ✅
position: fixed;     ✅

/* 不会触发 BFC */
position: relative;  ❌
position: static;    ❌
```

#### 3. will-change 使用场景

| 场景 | 建议 |
|------|------|
| 频繁动画的元素 | ✅ 加上 will-change |
| 偶尔动画的元素 | ⚠️ 只用 transform 即可 |
| 大量元素（1000+） | ❌ 不要滥用（内存爆炸） |

### 三、用户追问记录

#### 追问 1：DOM 和 CSSOM 并行构建原理

**用户问题：**
> JS 不是只有一个主线程吗？如何并行构建？

**完整解答：**

```
┌─────────────────────────────────────────────────────────────┐
│              浏览器多进程架构                                │
├─────────────────────────────────────────────────────────────┤
│  Browser Process（浏览器进程）                               │
│  ├─ Network Thread（网络线程）                              │
│  ├─ Storage Thread（存储线程）                              │
│  └─ ...                                                    │
│                                                              │
│  Renderer Process（渲染进程）← 每个 Tab 一个                 │
│  ├─ Main Thread（主线程）                                   │
│  │   ├─ HTML Parser（HTML 解析器）                          │
│  │   ├─ JavaScript Engine（JS 引擎）                        │
│  │   └─ Style Calculator（样式计算）                        │
│  ├─ Compositor Thread（合成线程）                           │
│  ├─ Raster Thread（光栅线程）                               │
│  └─ ...                                                    │
└─────────────────────────────────────────────────────────────┘
```

**关键澄清：**
- 说法"DOM 和 CSSOM 并行构建"不够准确
- 更准确：CSS 下载和 HTML 解析可以交错进行（不同线程）
- DOM 和 CSSOM 构建在主线程上是交替进行的
- JavaScript 会阻塞 HTML 解析

**时间轴：**
```
T0: 收到 HTML 响应头
T1: Network Thread 开始下载 HTML 数据
T2: Main Thread 开始解析 HTML → 构建 DOM
T3: 遇到 <link rel="stylesheet">
    ├─ Network Thread 继续下载 CSS（后台线程）
    └─ Main Thread 继续解析 HTML（不等待 CSS 下载完成）
T4: CSS 下载完成
    └─ Main Thread 解析 CSS → 构建 CSSOM
T5: DOM 和 CSSOM 都准备好后
    └─ 构建 Render Tree
```

#### 追问 2：will-change vs transform

**用户问题：**
> 只用 transform 不可以吗？为什么要加 will-change？

**完整解答：**

**答案：** 可以只用 transform，但效果可能不够好。

**对比图：**
```
只用 transform（不加 will-change）：
  滚动事件 → JS 修改 transform → 浏览器检测到变化
                              ↓
  浏览器：「哦，这个元素要动画？那我创建一个合成层吧」
                              ↓
  创建合成层（需要时间）→ 执行动画
                              ↓
  结果：第一帧可能卡顿

使用 will-change: transform：
  提前告知浏览器 → 浏览器提前创建合成层
                              ↓
  滚动事件 → JS 修改 transform → 直接使用已有合成层
                              ↓
  结果：流畅动画
```

**代码对比：**
```css
/* 方案 A：只用 transform */
.navbar {
  position: fixed;
  top: 0;
  transition: transform 0.3s;
}
/* 问题：第一次触发动画时，浏览器需要临时创建合成层 */
/* 可能导致首帧延迟 */

/* 方案 B：will-change + transform */
.navbar {
  position: fixed;
  top: 0;
  will-change: transform;  /* 提前告知 */
  transition: transform 0.3s;
}
/* 优势：浏览器提前准备，动画更流畅 */
```

**使用建议：**
| 场景 | 建议 |
|------|------|
| 频繁动画的元素 | ✅ 加上 will-change |
| 偶尔动画的元素 | ⚠️ 只用 transform 即可 |
| 元素很多（1000+） | ❌ 不要滥用（内存爆炸） |

**什么时候可以不用 will-change？**
```css
/* 情况 1：元素已经有其他触发合成层的属性 */
.navbar {
  position: fixed;
  transform: translateZ(0);  /* 已经创建合成层 */
}
/* 可以不用 will-change */

/* 情况 2：动画不频繁或对性能要求不高 */
.button {
  transition: transform 0.2s;  /* 短暂动画，不需要优化 */
}

/* 情况 3：元素很多，滥用会浪费内存 */
/* ❌ 错误用法 */
* { will-change: transform; }  /* 每个元素都创建合成层 = 内存爆炸 */
```
